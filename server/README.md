# VideoDrop на сервере — предварительная версия 2.0

Отдельный Telegram-бот, постоянная очередь SQLite, журнал заданий и ограниченное временное хранилище. Hermes не требуется для обработки файлов. Локальная версия 1.5.2 продолжает работать отдельно.

## Сценарии

- Пользователь нажимает `/start`; владелец получает кнопки допуска/отказа. Авторизация привязана к Telegram ID.
- Одно задание — одна обновляемая карточка в Telegram и готовый файл. ID карточки хранится в SQLite и переживает перезапуск. Выбор качества редактирует ту же карточку; подтверждения выбора отдельными сообщениями не отправляются. После завершения, отмены или истечения срока кнопки удаляются. Старые/повторные нажатия дают краткую всплывающую подсказку, без новой ошибки в чате и повторной отправки файла.
- В карточке только название, разрешение, вес и доступные действия. «Получить ссылку» появляется после подключения YouTube; недоступная выдача большого файла также не предлагается. Кодеки поясняются одной короткой строкой под готовым файлом только при возможной несовместимости. Диагностические ошибки и ID заданий не выводятся в обычном сценарии, но остаются в журнале. История тестовых сообщений предыдущих версий автоматически не удаляется.
- Видео сначала скачивается на сервер, затем в Telegram появляются «Получить ссылку» / «Получить файл». В сообщении указан фактический размер. При изменении качества или формата после скачивания файл скачивается заново по явному выбору пользователя.
- В «Качество и формат» рядом с разрешением указан вес видео вместе со звуком. Для уже скачанного варианта — фактический размер, для остальных — оценка с `≈` по размерам выбранных потоков или длительности и битрейту. Если данных недостаточно, выводится «размер неизвестен». Объединение и смена контейнера могут изменить итоговый размер. Доступны также разрешения вертикальных роликов; размер видео не показывается для аудиоформатов.
- «Получить ссылку» для владельца и допущенных сотрудников всегда означает загрузку в подключённый YouTube-канал с доступом `unlisted`. Серверная ссылка на скачивание никогда не подменяет этот вариант. Сотрудник получает ссылку на конкретный ролик, без доступа к настройкам или OAuth канала.
- «Получить файл» в Telegram: документ без повторного кодирования, если он проходит по размеру; иначе прямая HTTPS-ссылка на скачивание файла с сервера, действующая 24 часа. Рабочий предел обычного Bot API — 45 MiB. Качество не снижается для попадания в лимит.
- В режиме «Лучшее» выбираются лучшие доступные видео и звук независимо от расширения потока. MP4 не даёт приоритета менее качественному MP4/M4A на источнике; объединение выполняется без перекодирования. Более качественный готовый поток с видео и звуком также имеет приоритет перед менее качественными раздельными потоками. Явно выбранный предел разрешения сохраняется.
- Перед отправкой видео проверяется наличие настоящей видеодорожки через FFprobe (обложка аудио не считается видео); сохраняются фактическое разрешение и кодеки. Для VP9/AV1 бот предупреждает о возможной несовместимости с QuickTime и показывает размер кадра. Расширение `.mp4` само по себе не гарантирует совместимость. По умолчанию исходник не перекодируется и разрешение не уменьшается.
- Для задания из расширения способ получения выбирается до отправки: `mode=link` для YouTube, `mode=file` для прямой ссылки на скачивание независимо от размера. Сервер сам выставляет `entrypoint=extension` для API-заданий. `GET /api/jobs/<id>` возвращает статус и готовые ссылки владельцу задания; чтение результата не продлевает хранение.
- Посты Instagram: оригинальные фотографии через штатный парсер публичной страницы/авторизованной сессии yt-dlp, в исходном порядке, без текста поста и обложек видео. Пост с одним видео по адресу `/p/` обрабатывается как видео. TikTok-фотопосты распознаются также по адресам `/video/`, которые иначе возвращали только музыку. Картинки проверяются декодером и отправляются файлами без выбора YouTube.
- Без настроенного HTTPS большой файл не выдаётся по прямой ссылке: бот сообщает причину и сохраняет готовый файл на 24 часа. На текущем сервере HTTPS для файлов уже подключён. YouTube требует отдельного подключения.
- При отправке нескольких изображений сохраняется прогресс по файлам. В случае неопределённого ответа повторная отправка автоматически не производится.

## Журнал и роли

`/history` — свои задания. `/audit` — последние задания сотрудников. `/audit TELEGRAM_ID` — конкретный сотрудник. `/users` — допуск/отключение. `/export` — CSV всех заданий. `/status` — очередь и объём хранения.

Журнал содержит время, Telegram ID, имя/username, ссылку на источник без секретных query-параметров, название, формат, разрешение, выбранный способ выдачи, размер и результат. События: запрос, готовность файла, доставка в Telegram, подтверждение YouTube, запрос скачивания файла, отмена и удаление по сроку. Доставка не означает просмотр ролика. Бот заранее сообщает пользователям о журнале. Личные чаты и прочие действия сотрудников не читаются.

Куки источников зашифрованы, передаются в дочерний процесс через stdin и удаляются из очереди после завершения/ошибки. OAuth-токен YouTube зашифрован, принадлежит только серверу. В журнал, экспорт и ответы API секреты не попадают.

## Хранение и восстановление

Один тяжёлый процесс; не больше 20 активных заданий суммарно и 3 на человека. Общий бюджет 20 GiB, одно задание до 8 GiB, резерв свободного места 2 GiB. Лимиты проверяются во время скачивания. Временный файл по ссылке — 24 часа с момента выдачи ссылки; ошибка доставки и ожидание выбора — также 24 часа. После подтверждённой доставки в Telegram файл удаляется. После YouTube — только после проверки канала, доступа `unlisted`, завершения обработки и отправки ссылки пользователю.

Ссылка перестаёт работать по истечении срока. Очистка файлов запускается каждые 30 секунд независимо от долгих скачиваний и загрузок; чтение результата не продлевает срок.

После перезапуска скачивание возобновляется новым запуском в своей папке. Отправка, которая могла уже завершиться, переводится в «Нужна проверка», чтобы не создать дубликат. Автоматический повтор публикации не выполняется. Метаданные журнала остаются после удаления медиа.

## Установка

1. Скопировать исходники в отдельный каталог `/srv/apps/videodrop`.
2. Создать `server/.env` по `.env.example`, указать ID владельца и токен **отдельного** бота. Токен Hermes не использовать.
3. `server/data` должен принадлежать UID/GID `10001:10001`, права `700`. `.env` — `600`.
4. От root установить `server/network-guard.sh` в `/usr/local/sbin/videodrop-network-guard`, а `server/videodrop-network-guard.service` — в `/etc/systemd/system/`. Выполнить `systemctl daemon-reload` и `systemctl enable --now videodrop-network-guard`. Он ограничивает только мост `br-videodrop`, блокируя обращения контейнера к внутренним сетям и хосту.
5. `docker compose -f server/compose.yaml up -d --build`.
6. Проверить `curl http://127.0.0.1:8787/health`. Поля `telegramConfigured`, `telegramConnected`, `youtubeConnected` различают установленный процесс и подключённые сервисы.

Порт приложения публикуется только на `127.0.0.1:8787`. Пустой `VIDEODROP_PUBLIC_URL` полностью отключает публичные маршруты. Для Telegram с большими файлами установить HTTPS-адрес в `VIDEODROP_PUBLIC_URL` и `VIDEODROP_PUBLIC_MODE=files`: доступны только подписанные ссылки `/download/`, API расширения и OAuth callback остаются закрыты. Режим `all` потребуется при отдельном подключении расширения.

На хосте установлен Caddy из репозитория Ubuntu. `server/Caddyfile` проксирует GET/HEAD `/download/*`, интерфейс `/app/*` и перечисленные маршруты API расширения. Остальные внешние маршруты, включая `/health` и `/oauth/callback`, возвращают 404. Имя задаётся через `VIDEODROP_DOWNLOAD_HOST` в systemd override Caddy; токены бота туда не передаются. Для первоначального адреса используется бесплатный DNS [sslip.io](https://sslip.io/) с IP сервера, TLS выпускается и продлевается [Caddy](https://caddyserver.com/docs/automatic-https). Этот адрес зависит от доступности внешнего DNS; позже можно заменить его собственным доменом. Открыты только TCP 80/443 дополнительно к существовавшему SSH. Изоляция сети загрузчика не менялась. URL с токенами исключены из журналов запросов.

## Серверное расширение Chrome — 2.0.0-preview.8

`extension-server/` — самостоятельная оболочка без localhost, общего ключа, native messaging, debugger и автоматизации Studio. Перед сборкой Docker выполнить `.venv/bin/python scripts/build_server_extension.py`; ZIP попадёт в `/app/VideoDrop-Chrome.zip`. Для интерфейса и API нужен `VIDEODROP_PUBLIC_MODE=all`. `files` остаётся режимом без расширения.

Вход через бота: `/pair` или deep link `?start=connect`. Одноразовый код живёт 10 минут, API-токен — 90 дней. Токен хранится в доверенных контекстах Chrome storage.local, не синхронизируется. Блокировка сотрудника отзывает его токены. Выход отзывает только текущий токен.

Сначала `/api/jobs` с `prepare=true` проверяет источник без скачивания файла. Затем `/api/jobs/:id/start` атомарно принимает формат, высоту и способ получения. Повторное нажатие не запускает дубликат. Для Chrome файлы выдаются по HTTPS на 24 часа; сообщения в рабочий Telegram-чат не дублируются. Журнал владельца сохраняет сотрудника и исходную ссылку.

Интерфейс `/app/` работает в отдельном iframe без доступа к Chrome API. Оболочка принимает сообщения только от точного origin сервера и своего iframe; доступ к cookies включается отдельной нативной галочкой. Передаётся выбранный адрес из обнаруженного списка и cookies страницы/плеера. Произвольные URL и код через мост не исполняются. Смена страницы делает прежний контекст недействительным.

«Обновить» перезагружает серверный UI с Cache-Control: no-store. Сам код оболочки не может обновляться с GitHub в обычном Chrome macOS/Windows: для него нужна замена файлов или Chrome Web Store/корпоративная политика. Выбор YouTube включается только после подключения канала.

## YouTube

Требуется Google Cloud проект, YouTube Data API и OAuth-клиент. Личный Google-аккаунт подходит. Для режима только Telegram создать OAuth-клиент типа Desktop app и выполнить на компьютере `.venv/bin/python scripts/connect_server_youtube.py --client /absolute/path/client.json --host contabo-main`. Скрипт сохраняет адрес входа во временный файл `.server-state/youtube-authorization-url.txt`; открыть его в браузере, выбрать канал и дать разрешение. Локальный callback принимает ответ Google, проверяет канал и сохраняет зашифрованное разрешение на сервер через SSH. После этого компьютер не нужен. Адрес входа автоматически удаляется; токены не печатаются.

Для будущего веб-подключения клиентский JSON типа Web сохраняется только в `server/data/youtube-client.json`, callback — `https://YOUR-HOST/oauth/callback`. `/youtube` выдаёт одноразовый адрес входа на 10 минут.

Запрашиваются `youtube.upload` и `youtube.readonly`: загрузка и проверка результата/канала. Каждая отправка явно устанавливает `unlisted` и `notifySubscribers=false`. Ролики считаются не предназначенными для детей. Сначала нужен тест на реально подключённом канале; доступ `unlisted` нельзя считать подтверждённым по наличию кода.

## Проверка

`.venv/bin/python -m unittest discover -s tests -p 'test_server.py' -v`

Проверяются разделение пользователей, запрет администрирования сотрудникам, шифрование и редактирование секретов, одноразовая привязка, отмена/истечение срока, сохранение файлов при ошибке, отсутствие повторной публикации после рестарта и закрытость HTTP в Telegram-only режиме. Это не заменяет реальную проверку Telegram и YouTube с подключёнными аккаунтами.

Версия `2.0.0-preview.2` установлена с исправленным выбором способа получения. Повторная проверка того же MP4 подтвердила порядок: `download_ready` → ожидание выбора с готовым файлом → `selected` → `telegram_file_delivered`. OAuth YouTube ещё не настроен. Скачивание публичного тестового YouTube-видео с IP сервера потребовало подтверждения входа. Подключение API для загрузки не решает авторизацию скачивания. Reels, TikTok и посты с картинками требуют отдельной проверки на рабочих ссылках; наличие обработчиков не означает, что площадка разрешит серверу получить любой пост.

Проверка Instagram Reels выявила отдельную границу совместимости: готовый MP4 содержал VP9 1080×1920 и AAC, корректно декодировался FFmpeg, но QuickTime открывал только звук. Для этого ролика нативный H.264 доступен у Instagram лишь в 720×1280; его отдельная копия отправлена владельцу с явной пометкой разрешения и открыта в QuickTime с изображением. Владелец выбрал сохранение максимального качества для монтажа и повторной загрузки. Автоматическая замена исходника на менее высокое разрешение или перекодирование не выполняется. Проверки версии `2.0.0-preview.4` охватывают отказ от отправки файла без видеодорожки, предупреждение о кодеке, сохранение проверенных характеристик после удаления файла и отсутствие приоритета менее качественного MP4-потока.

Версия `2.0.0-preview.5`: 102 Python-проверки; вес рядом с качеством проверен в живом боте. Instagram `DO_JtFTEidP` не сообщает длительность и размеры потоков заранее: после FFprobe исходника 1080×1920 меню показывает фактические 5.3 МБ для «Лучшее» и оценки 3.7 / 2.4 / 1.2 МБ для меньшей высоты кадра. Оценка учитывает звук и не требует скачивать каждый вариант.

TikTok `7696882267716619540` первоначально возвращал `Unexpected response from webpage request` в yt-dlp 2026.10.21; добавление curl_cffi не помогло. При этом обычный GET публичной страницы возвращает данные ролика. Добавлен ограниченный резервный путь только для этой ошибки на прямых TikTok-ссылках: обычный запрос без переходов, проверка публичного статуса и совпадения ID, затем штатный парсер и выбор форматов yt-dlp. Закрытый статус, требование входа, другой ID или слишком большая страница не принимаются. Тестовый файл 1 209 232 байт, H.264/AAC, 576×1024 (лучшее доступное по этой ссылке) полностью декодирован, доставлен документом в Telegram; временная копия удалена, журнал сохранён. YouTube Shorts `q9H63HxY3ag` по-прежнему требует подтверждения входа с IP сервера — скачивание этой ссылки не подтверждено.

Версия `2.0.0-preview.6` упрощает переписку и закрывает повторное использование кнопок завершённых заданий. Проверки выполняются с изолированной очередью и имитацией Telegram: полный цикл использует один message_id, повторные нажатия не создают сообщений или отправок, старые карточки не меняют актуальное задание, чужие кнопки не дают доступа, ID переживает миграцию/перезапуск, ошибки редактирования не порождают дубликаты. Новые тестовые файлы в рабочий чат владельца не отправляются. Это изменение интерфейса не снимает ограничение скачивания YouTube и не подключает OAuth/HTTPS.

Для отдельного тестового чата требуется доступ к разблокированному Telegram на Mac.

JSON-строки рабочего процесса сериализуются под общей блокировкой: параллельные HLS/DASH-фрагменты больше не смешивают события. Для HLS с неизвестным битрейтом звука оценка веса остальных разрешений дополняется фактическим битрейтом из готового файла; неизвестный звук не исключается из расчёта. Пройдено 124 автоматические проверки. OAuth YouTube, серверная авторизация источников и миграция Chrome-расширения остаются отдельными незавершёнными подключениями.

Живая проверка HTTPS: весь файл 636 123 766 байт скачан извне; SHA-256 совпал с оригиналом. HEAD возвращает 200 и верный Content-Length, Range — 206. Внешние `/health`, `/api/jobs`, `/api/pair`, `/oauth/callback` возвращают 404. По окончании проверен отказ по истёкшей ссылке и удаление файла. Тестовое задание имеет `telegram_message_id=0`: новых сообщений в рабочий чат не отправлялось. После проверки временное хранилище очищено. Перед пересозданием контейнера активных заданий не было; прежние 8 заданий, 31 событие и 1 пользователь сохранились. Caddy и Hermes работают независимо от загрузчика.

## Серверный клиент: проверка 27 октября 2026, preview.8

Новая оболочка Chrome 2.0.0 находится в `extension-server/`; прежний локальный клиент не входит в её архив. Сервер переключён в `telegram-and-extension`. `/app/` и архив доступны по HTTPS; API заданий, сессии и журнала требует персональный токен. `/health` и `/oauth/callback` снаружи остаются закрыты. Одноразовый код выдаёт бот командой `/pair` только допущенному пользователю. Сотрудник получает допуск через «Запустить» → запрос владельцу → «Разрешить»; управление доступом — `/users` у владельца.

Через серверный интерфейс в настоящем Chrome проверены привязка владельца, сохранение входа после «Обновить», выбор качества до скачивания и получение результатов:

Файлы доступны 24 часа; задания расширения не создают технических сообщений в Telegram. Неавторизованные запросы к сессии, заданиям и журналу возвращают 403. Архив содержит только семь разрешённых файлов, без локальных токенов и Studio-драйвера; его SHA-256 совпал с серверным. Пройдено 135 Python- и 26 JavaScript-проверок.

При проверке исправлена гонка подсчёта места с переименованием временного файла загрузчиком. Зависимости загрузчика закреплены на проверенных версиях: yt-dlp 2026.10.21, gallery-dl 1.32.18, imageio-ffmpeg 0.6.0. Обновление образа не должно незаметно менять загрузчик. `server/web` подключён к контейнеру только для чтения: изменения интерфейса можно доставлять без прерывания очереди.

Граница проверки: серверный интерфейс и реальные файлы проверены; загрузка оболочки через `chrome://extensions`, чтение вкладки и передача cookies из установленной оболочки ещё требуют ручной проверки. Инструмент автоматизации запретил открывать внутреннюю страницу Chrome. Это ограничение инструмента, а не запрет пользователю установить расширение. YouTube OAuth пока не подключён, а скачивание YouTube с серверного IP по-прежнему может требовать входа; недоступная загрузка на YouTube отключена в интерфейсе.

Обновление интерфейса 27 октября: в окне расширения вместо выпадающего списка отображаются карточки найденных источников с кнопкой «Выбрать»; история свёрнута. Если связь серверной страницы с оболочкой не установилась, показывается подсказка об обновлении. Файлы интерфейса заменяются на сервере без перезапуска загрузчика. Работу серверной страницы и проверку ограничений YouTube нужно отличать от проверки установленной оболочки Chrome.
